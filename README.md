## 1. code-review：多智能体四视角代码审查

单人视角会漏问题。本 skill 让四个"专家人格"**并行**审查同一段改动，再由主智能体**回读源码逐一核实**，输出可追溯的审查报告。

### 四个视角

| 视角 | 审查什么 |
|------|----------|
| **架构与分层** | 分层是否清晰、依赖方向、抽象边界、可扩展性、命名 |
| **正确性与边界** | 算法/协议/业务逻辑、空值、越界、异常路径、边界条件 |
| **线程与资源** | 并发安全、竞态、锁/定时器、文件句柄、内存、退出清理 |
| **交互与体验** | UI 布局、状态反馈、错误提示、误操作防护、无障碍 |

视角可按项目类型替换：非 UI 项目把第 4 个换成**测试与可测性**；协议项目重点看帧解析边界、字节序、CRC；嵌入式项目重点看栈/堆、看门狗、IO 时序。

### 核心纪律

- **并行发起**：在同一条消息里发出 4 个子智能体调用，并发执行
- **prompt 自带上下文**：子智能体看不到对话历史，需明确列出要读的文件、具体核对点、输出格式与字数上限
- **主智能体必须核实**：子智能体的结论不一定准确，每条严重结论都要回读源码确认，误报要在报告中标注澄清
- **问题分级**：P0 严重（立刻修）/ P1（本轮必修）/ P2 建议 / P3 可选
- **配套产出**：每轮生成 `审查报告N.md` 并同步更新 `版本说明.md`（feat → minor+1，fix → patch+1，破坏性变更 → major+1）

### 完整流程

```
实现功能 → 跑测试 → 四视角并行审查 → 回读源码核实 → 当场修复并复测
→ 写审查报告 → 更新版本说明 → 询问用户修复范围 → 按 conventional-commit 规范提交
```

## 2. conventional-commit：Conventional Commits 提交规范

规范的提交信息是项目的第一手文档：三个月后回看 `git log`，一眼就知道"这次为什么改、改了什么"。

### 格式

```
<类型>(<范围>): <描述>

<正文：为什么改 / 改了什么 / 怎么验证>

<脚注：BREAKING CHANGE / Closes / Co-authored-by>
```

### 常用类型与版本号联动

| 类型 | 用于 | 版本号影响 |
|------|------|------------|
| `feat` | 新功能 | **minor +1**（1.2.0 → 1.3.0） |
| `fix` | 修 bug | **patch +1**（1.3.0 → 1.3.1） |
| `docs` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` | 文档 / 重构 / 性能 / 测试 / 构建 / 流水线 / 杂项 | 不变 |

**破坏性变更**：类型后加 `!` + 脚注 `BREAKING CHANGE:` → **major +1**（1.x → 2.0.0）。

### 示例

```bash
fix(protocol): LEN 超限判错并重同步, 防止吞帧

伪造的大 LEN 会让解析缓冲长时间等一个永远到不了的帧,
期间到达的正常帧被连带丢弃。

- 新增 MAX_PAYLOAD=64 上限, 超限按错误帧处理并计数
- 补测试: 伪造 LEN=255 后紧跟正常帧, 验证正常帧仍被解析

测试: python tests/test_protocol.py (12 项全过)
```

### 关键要点

- 描述**中文、动词开头、≤ 50 字**、结尾不加句号，拒绝 `update` / `fix bug` 这类无信息描述
- 范围用目录名或模块名（如 `ui`、`protocol`），一眼定位改动位置
- 复杂改动必写正文三段式：**为什么改 / 改了什么 / 怎么验证**
- 一次提交只干一件事，不把重构和功能混在一起

## 3. km1-robot-arm：KM1 机械臂 Python 控制

面向 **松甲机器人 KM1 / Yeahbot / YHKPZAR** 协议族的六轴机械臂（6 路舵机，USB 虚拟串口 115200）。把踩过的坑固化成"铁律 + 速查表"，不用每次对着原始文档重新推。

**机械臂本体分 PWM 版和总线版**，客户刚拿到机器时先问这一句——两版运动指令写法一样，自检流程不同：

| 版本 | 首次自检 |
|---|---|
| PWM 版 | 问安装是否正常 → 6 个 id 全给 `P1500` → 问是否**垂直向上** → 逐个 id 小幅度点动，查有没有接错线 |
| 总线版 | **先发 `#000PID!`~`#005PID!` 查 6 个 id 的回报**，正常后再走上面那套 |

自检通过前不要跑 `$DGS` / `$DGT` 预设动作组——整机联动，接线错位会让关节互相打。

**控制器又分三款：ESP32 / Arduino / STM32。** 三款串口指令**完全兼容**（协议前缀、零填充格式、返回数据、角度换算全部一致），同一份控制代码可以原样跑在三款上；**唯一差异是开串口时 `dtr` / `rts` 的取值**。

| 控制器 | 串口芯片 | `dtr` | `rts` | 说明 |
|---|---|---|---|---|
| ESP32 单片机 | ESP32-S3 原生 USB CDC | `False` | `False` | 不禁用就进下载模式，只吐 `waiting for download` |
| Arduino 单片机 | 板载 USB 转串口 | 不设置 | 不设置 | 自动复位靠 DTR 脉冲，板子自己处理 |
| STM32 单片机 | CH340X | `True` | `False` | DTR#→BOOT0、RTS#→经 1N5819WS→RESET；`dtr` 不给 True 会停在 bootloader |

SKILL 里还给了 `reset_stm32()`（BOOT0 只在复位时采样，改了 `dtr` 必须复位一次）和一个依次尝试四种组合直到固件回话的自动探测函数——型号不明也能直接跑通。

### 三条铁律

| # | 铁律 | 不遵守的后果 |
|---|------|--------------|
| 1 | `dtr` / `rts` 按控制器型号配（三款唯一差异） | 配错即进下载模式（只吐 `waiting for download`）、被按在复位里，或 STM32 停在 bootloader，发指令零回应 |
| 2 | 结束符不能错：命令/动作 `!`，批量 `}`，存储 `>` | 少一个符号 = 指令没发出去 |
| 3 | 动手前先发 `$DST!` | 上电会自动播放默认动作组，你的单舵机指令被抢回中位 |

### 协议速查

```
$DST!                 停止所有动作
$DGS:3!               执行第 3 组预设动作
$DGT:1-5,1!           执行 1~5 组，各 1 次
#003P1500T0500!       3 号舵机 → PWM 1500 → 500ms 到位
{#000P...!#001P...!}  同时控制多舵机
$RST!                 重启控制板
```

舵机映射：0 底座旋转 / 1 大臂 / 2 小臂 / 3 腕部俯仰 / 4 腕部旋转 / 5 夹爪。角度换算：`PWM = 500 + 角度 × 2000/180`。

### 收录内容

- **PWM 版 / 总线版自检流程**：先问版本 → 全中位姿态确认 → 逐个 id 小幅度点动查接线；总线版多一步 `#000PID!` 查 ID 与回报
- 硬件规格与角度/PWM 换算（含 Python 函数）
- **三款控制器对照**：ESP32 / Arduino / STM32 命令完全兼容，只有 DTR/RTS 不同；含 STM32 的 CH340X 接线推演、`reset_stm32()`，以及四种组合自动探测（会排除"下载模式"假阳性）
- 连接铁律 + 常见错误对照表（端口占用、下载模式、无响应、缺驱动）
- 指令协议详解：四种模式前缀、单舵机零填充格式、批量、返回数据格式
- 可直接复用的 `RobotArm` 控制类与动作序列编排模板
- 从固件 dump 预设动作组的方法（`$DGT:10-19,1!` → `@GroupDone!`）
- Windows / Linux 差异与端口自动检测
- 故障排查表 + 工程纪律（判定完成认 `@GroupDone!`，不要 `sleep` 猜）

## 安装与使用

1. 将 skill 文件夹（含 `SKILL.md`）复制到你的 AI 工具的 skills 目录，例如：
   - Trae：项目 `.trae/skills/` 或全局 skills 目录
   - Claude Code：`~/.claude/skills/`
   - WorkBuddy：`~/.workbuddy/skills/`（用户级）或 `<项目>/.workbuddy/skills/`（项目级）
2. 无需额外配置，skill 会在匹配场景（代码审查、编写提交信息、机械臂控制/调试）自动触发，也可在对话中点名调用。
