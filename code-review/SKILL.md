# 多智能体四视角代码审查

单人视角会漏问题。让四个"专家人格"并行审查，再由主智能体回读源码核实，输出可追溯的审查报告。

## 一、何时触发

- 完成**较大功能 / 重构 / 批量修复**之后（不论用户是否要求）
- 用户说"审查一下 / 有没有问题 / 把把关"
- 提交或发布前的最后一道关

文档级小改动、纯答疑不需要走完整流程。

## 二、四个视角（可按项目类型替换）

| 视角 | 审查什么 | 典型发现 |
|------|----------|----------|
| **架构与分层** | 分层是否清晰、依赖方向、抽象边界、可扩展性、命名 | UI 直连具体实现、循环依赖、类名与职责不符 |
| **正确性与边界** | 算法/协议/业务逻辑、空值、越界、异常路径、边界条件 | 校验和算错、空列表崩溃、异常吞掉、缓冲区无界 |
| **线程与资源** | 并发安全、竞态、锁/定时器、文件句柄、内存、退出清理 | 关端口后队列信号污染新会话、terminate 丢资源、无界增长 |
| **交互与体验** | UI 布局、状态反馈、错误提示、误操作防护、无障碍 | 错误提示在循环里刷屏、同引脚不校验、控件层级不一致 |

**非 UI 项目**：把第 4 个视角换成 **测试与可测性**（覆盖率、测试确定性、能否离线回归、mock 边界）。
**协议/通信项目**：第 2 个视角重点看帧解析边界、字节序、CRC、超时与重试。
**嵌入式项目**：第 3 个视角重点看栈/堆、看门狗、IO 电平与时序。

## 三、执行方式

**在同一条消息里并行发起多个 Agent 调用**（它们会并发跑）：

```bash
# 伪代码示意：一条消息内发 4 个 Agent 调用
Agent(subagent_type="general-purpose", description="架构与分层审查", prompt="...")
Agent(subagent_type="general-purpose", description="正确性与边界审查", prompt="...")
Agent(subagent_type="general-purpose", description="线程与资源审查", prompt="...")
Agent(subagent_type="general-purpose", description="交互与体验审查", prompt="...")
```

### 子智能体 prompt 怎么写

必须自带上下文（子智能体看不到你们的对话）：

```bash
你是一名资深嵌入式工程师，精通 STM32 AN3155。这是第三轮审查：验收协议层修复并扫描新问题（只分析，不改文件）。

需求背景：<一句话说明这轮改了什么>
请完整阅读：
- <文件1: 说明它管什么>
- <文件2: 说明它管什么>
- <测试文件: 说明覆盖了什么>

核对：1) <具体核对点>；2) <具体核对点>；3) <边界场景>

输出：【验收结果 / 新问题(严重/建议/可选)】，每条含 文件:行号，500 字以内。
```

要点：
- 明确写"**只分析，不改文件**"
- 列出要读的文件和每个文件的作用（别让子智能体自己猜）
- 给出**具体核对点**而不是"看看有什么问题"（否则输出全是泛泛而谈）
- 限定输出格式和字数（严重收敛，防止刷屏）
- 有上一轮报告的话，让它"验收上一轮修复是否落地 + 扫描新问题"

## 四、主智能体的核实纪律（**最重要的环节**）

> 子智能体的**结论不一定准确**。它可能误报、可能看漏、可能引用不存在的行号。

1. 对每一条 **严重 / 关键结论**，**必须回读源码核实**（Read/Grep 定位到那几行）
2. 确认是真问题 → 写进报告；确认是误报 → **在报告里标注"已核实为误报"及原因**
3. 顺手检查子智能体**漏掉的**高危点（线程退出、资源释放、异常吞没）
4. 报告里的每个"文件:行号"都要真实存在

## 五、问题分级

| 级别 | 判定 | 处理 |
|------|------|------|
| **P0 严重** | 数据丢失 / 崩溃 / 协议错误 / 安全问题 | 立刻修 |
| **P1** | 明显 bug、内存/线程隐患、错误提示误导 | 本轮必修 |
| **P2 建议** | 可维护性、体验、边界未覆盖 | 建议本轮修，可批量 |
| **P3 可选** | 锦上添花 | 记录进遗留清单 |

## 六、审查报告模板（`审查报告N.md`，N 递增，旧报告全部保留）

```markdown
# <项目名> 代码审查报告（第 N 轮 · <本轮主题>）

> 流程：四视角并行审查 → 主智能体回读源码核实 → 问题当场修复并复测
> 日期：YYYY-MM-DD · 需求：<本轮改了什么>

## 一、本轮改动
- 功能/结构调整概要

## 二、审查发现与处置
| # | 视角 | 问题 | 处置 |
|---|------|------|------|
| 1 | 架构 | <问题> | ✅ <怎么修的> |

## 三、误报澄清
- 某智能体报告的 XX 问题，经回读源码确认为误报：<原因>

## 四、测试
- 新增/修改的测试项 + 总体结果

## 五、遗留
- 本轮不做的问题及原因（分优先级）

## 六、结论
- 修了几个、留了几个、能否发布
```

## 七、配套产出（**强制**）

每轮审查后必须同步更新两份文档，否则流程视为未完成：

1. `审查报告N.md` —— 本报告
2. `版本说明.md`（或 CHANGELOG）—— 版本表追加一行 + 版本详情追加一节

版本号规则：**feat → minor+1，fix → patch+1，破坏性变更 → major+1**。

## 八、完整流程（可直接照做）

```
1. 实现功能
2. 跑测试（逻辑模块直接断言；UI 用离屏冒烟；协议类做模拟器）
3. 四视角并行审查（本 skill）
4. 回读源码核实 → 当场修复 → 复测
5. 写 审查报告N.md
6. 更新 版本说明.md
7. present_files 展示报告与改动
8. 询问用户修复范围（P1 全修 / 只修 P0 / 全量含重构 / 暂不修）—— 大改动别擅自扩大范围
9. 需要提交时，按 conventional-commit skill 写提交信息
```

## 九、测试配套纪律

- **测试向量用代码生成**，不要手算（手算校验和出过两次错）
- **逻辑模块做到无硬件可测**：给传输层留注入点，写模拟器（如串口协议模拟器）
- **GUI 用离屏冒烟**：`QT_QPA_PLATFORM=offscreen` + 定时器退出
- **离屏测试要屏蔽模态弹窗**（QMessageBox 会挂起直到超时）
- **测试要确定性**：清掉跨运行残留（配置/缓存），别依赖注册表或本地状态

## 十、环境红线（本机已知坑）

- **禁用 `git rebase` / `cherry-pick` / `reset --hard`**：这些操作会大量重命名/删除 `.git` 内文件，可能触发沙箱保护把整个 `.git` 删掉（真实发生过）。只用 `init` / `add` / `commit` / `fetch` / `checkout` / `push`
- 整合远程已有提交时，用「`fetch` + `checkout -b main <remote-sha>` + 补提交」构造线性历史
- bash 里 `ls/cat/head/grep/wc` 常不可用 → 用专用工具或 Python
- 沙箱内 `pip install` 大包会触发删除保护 → 需提权重试
